# Семейный бюджет — заметки для разработки

## Что это
Одностраничное офлайн-приложение семейного бюджета. Весь код — в одном файле
`index.html` (HTML + CSS + JS, без сборки). Файл `family-budget-light.html`
держим **байт-в-байт идентичным** `index.html` (это копия для запасного URL).
После любой правки `index.html` нужно скопировать его поверх
`family-budget-light.html`.

## Хостинг и доставка
- Сайт публикуется через **GitHub Pages из ветки `main`** (workflow
  «pages build and deployment»).
- Рабочая версия пользователя — это и есть GitHub Pages. Изменения попадают
  к пользователю только после мёрджа в `main` и автодеплоя (1–3 мин).
- После деплоя часто нужен жёсткий рефреш браузера (Ctrl/Cmd+Shift+R) —
  кэшируется `index.html`.

## КРИТИЧНО: сохранность данных
Данные пользователя зашифрованы (E2E) и хранятся в localStorage/облаке.
**Нельзя терять данные и сбрасывать логин/пароль.**
- Формат данных менять только обратносовместимо.
- Новые поля подмешивать через `mergeDefaults()` (а не перезаписывать).
  Курсы валют мёржатся так: `d.rates={...defData().rates,...d.rates}` —
  поэтому новые курсы появляются у существующих пользователей, не затирая их.

## Облако (Supabase) и устойчивость к его падению
- Бэкенд — бесплатный проект Supabase (REST, таблица `budget`, строка `id='main'`,
  колонка `data` jsonb с зашифрованным конвертом, RLS открыта для `anon` —
  безопасно, т.к. данные E2E-зашифрованы).
- Конфиг: `CLOUD_DEFAULT` (url + публичный ключ `sb_publishable_…`) в коде. Адрес
  можно **переопределить из UI** (Настройки → Облако) — сохраняется в localStorage
  `cloud_cfg_v1`, читается `loadCloudCfg()`; `CLOUD` — `let`, не `const`.
  Это чтобы переподключить новый проект Supabase БЕЗ правки кода и редеплоя.
- Вход устойчив к недоступному облаку: при ошибке `cloudGet()` вход НЕ блокируется —
  грузим локальный зашифрованный кэш (`bali_v5`), офлайн-режим (`_cloudDown`,
  индикатор «☁︎ офлайн · сохранено»). Если облака нет И локальной копии нет —
  НЕ создаём пустые данные (иначе пустышка затрёт облако при его возврате).
- `persist()` всегда пишет localStorage ПЕРВЫМ (данные не теряются), потом облако;
  офлайн-правки до-синхронизируются, когда облако вернётся.
- Анти-пауза: `.github/workflows/keepalive.yml` пингует Supabase раз в ~3 дня.

### Авторитетность данных (КРИТИЧНО — против потери данных)
ОБЛАКО — авторитетный источник при входе/восстановлении (`loadEnvelopes`). Локальная
копия берёт верх ТОЛЬКО при несинхронизированных офлайн-правках (флаг `bali_v5_dirty`,
ставится в persist при неудачной заливке, снимается при успешной). Иначе грузится
облако, локальный кэш освежается. Это не даёт устаревшей локальной копии затереть
свежее облако (инцидент: вход офлайн по старой локали показал устаревшие данные).
Перед заливкой dirty-локали прежняя облачная версия сохраняется в `bali_v5_cloud_backup`.
НЕ возвращать выбор «по updated/таймстампу» — таймстамп локали бампается при офлайн-
правке и делает устаревшее «новее» (это и есть затирание).

### Ежедневный бэкап
Главный механизм — **облачные снимки** (`cloudSnapshot`): раз в день при входе в таблицу
`budget` пишется зашифрованная строка-снимок `id='bk-<date>'` (хранятся последние 30,
`pruneCloudSnapshots`). Надёжно, off-device, не требует ручного скачивания. Восстановление —
`restoreSnapshot(id)` (Настройки → Резервная копия → выбрать снимок), расшифровка тем же DEK.
Доп. копия — файл на диск (`xprt`, тумблер `#st-autobk`→`bali_v5_autobk`, best-effort, т.к.
авто-download в браузере ненадёжен). Браузерный снимок в localStorage УБРАН как неэффективный
(лежал там же, где данные). Офлайн не бэкапим. Guard «раз в день»: `bali_v5_cloudbkdate`.

### Runbook восстановления облака
1. Диагностика: `dig +short <ref>.supabase.co` — если NXDOMAIN при живом
   `supabase.com`, проект спит/удалён.
2. https://supabase.com/dashboard → проект. Если **Paused** → **Restore**
   (≤90 дней с паузы данные целы). Адрес/ключ те же → ничего в коде менять не надо.
3. Если проект пропал/удалён → создать новый, выполнить SQL таблицы (показан в
   Настройки → Облако), вставить новые URL+ключ в панель «Облако» (мгновенно для
   этого устройства). Для всех устройств — обновить `CLOUD_DEFAULT` в коде и
   задеплоить.
4. Логин/пароль при этом НЕ меняются: пароль — это ключ шифрования, он не привязан
   к проекту Supabase; данные при первом входе берутся из локального кэша (тем же
   паролем) и заливаются в новое/восстановленное облако.

## Валюты
Поддерживаются: **IDR** (база, рупия), **USD**, **THB** (тайский бат),
**UAH**, **USDT**, BTC, ETH.
Базовая валюта расчётов — IDR. Курсы хранятся в `D.rates`:
- `usdIdr` — рупий за 1 USD
- `thbIdr` — рупий за 1 THB
- `uahIdr` — рупий за 1 UAH
- `usdtUsd` — USD за 1 USDT

### Зафиксированные курсы по умолчанию (defData)
При курсе **1 USD = 17000 IDR**:
- `usdIdr: 17000`
- `thbIdr: 580` (бат зафиксирован относительно этого курса доллара)
- `uahIdr: 400`
- `usdtUsd: 1`

Эти же значения продублированы как запасные (fallback) в обработчике
сохранения курсов (`btn-save-rates`).

### Где трогать код при добавлении/правке валюты
- `defData().rates` — значения по умолчанию
- `toIdr(amt,ccy)` и `rateFor(ccy)` — конвертация в рупии
- `CSYM` — символ валюты, `CCOLS` — цвет в разбивке по валютам
- `calcAccTotals()` / `rAccTotals()` — сводка по счетам
- селект `#am-ccy` (создание счёта), селекты `#sn-ccy` / `#vo-ccy` (доход)
- модалка курсов `#m-rates` (поля `r-usd`/`r-thb`/`r-uah`/`r-usdt`) и её
  обработчики открытия/сохранения; онлайн-подтяжка в `fetchRatesOnline()`
- зачисление дохода на счёт: ветки расчёта `credited` в
  `applyEntryToBalances()` и `addInc()`

## Цели накоплений (savCats): сумма цели и закрытие
Цель: `{id,name,color,target,plan[12],closed?}`. `target` и `plan` — в **млн Rp**
(не в актуальных рупиях, в отличие от `accounts.bal`). Накоплено = `sum(plan)`.
- **Редактор** (Настройки → Цели накоплений) рисует не общий `rCatEd`, а отдельную
  ветку `rSavCatEd(el)` (для `type==='sav'`). Строки двухъярусные (`.sav-ed-row`):
  название + удаление сверху, «Цель, млн Rp» + статус + «Закрыть/Открыть» снизу.
  `data-i` берётся ДО сортировки (закрытые — вниз), чтобы обработчики не сбивались.
- **`closed`** — необязательное поле. Отсутствует у старых данных → цель активна
  (читается как falsy, миграция не нужна). Закрытие — только СТАТУС, плановые суммы
  и история не меняются; в графике «по месяцам» закрытые цели остаются.
- **Авто-закрытие**: `applyAutoClose()` при `settings.savAutoClose` помечает
  `closed=true` достигнутые цели (`sum(plan) >= target`). **Одностороннее** — назад
  не открывает (только вручную кнопкой «Открыть»). Вызывается в начале `rSav()` и
  `rSavCatEd()`; если что-то изменил — `autoSave()`.
- `closed` влияет на показ в `rSav()` (KPI + прогресс): закрытые сортируются вниз,
  затемняются, бейдж «✓ закрыто». Графики (`ch-sav-m`, `ch-sav-p`) НЕ трогаем — план.
- ⚠️ ПЛАН vs ФАКТ (важно — частый источник путаницы). У цели два измерения:
  - ПЛАН = `savTot(c)` = сумма `plan[12]` (сколько ПЛАНИРУЕТСЯ отложить). В редакторе и
    «Плане по целям» показывается как «по плану N%»; при `plan≥target` — нейтральное
    «📋 план собран» (НЕ «достигнута»! план ≠ реальные деньги). Рядом с % выводится и
    сумма по плану `fRp(savTot)` — удобно выставлять `target`.
  - ФАКТ = `goalRealIdr(c)` = Σ `potIdr` конвертов этой цели (реально отложено, сырые IDR).
    `goalReached(c)` = `goalRealIdr ≥ target*1e6`. Только это даёт «🎯 достигнута» —
    показывается в «Реальном остатке» (бейдж + «N% цели») и используется `applyAutoClose()`.
  Т.е. цель «достигнута»/авто-закрывается ТОЛЬКО когда деньги реально отложены в конвертах,
  а не когда план их покрывает. `target` в млн → сравнение с `goalRealIdr` через `*1e6`.
- ⚠️ `saveSettings()` пересобирает `D.settings` — использует `{...D.settings, …}`,
  чтобы не затирать `savAutoClose` (тумблер `#st-savauto` сохраняется при изменении).

## Конверты «Реальный остаток» (savPots) — подвкладка Накоплений
Вкладка Накопления разбита на 2 подвкладки переключателем `spSav(tab)` (`_savTab`,
по умолчанию `'plan'`): `#sav-pane-plan` (старое — `rSav`, не тронуто) и
`#sav-pane-real` (новое — `rPots`). Диспетчер `sp()`/`rAll()` для savings зовёт
`()=>spSav(_savTab)` (а не `rSav` напрямую) — оба места одинаковой строкой.
- **Конверт**: `D.savPots[] = {id, goalId, accId, amt, note}`. `goalId`→`savCats.id`,
  `accId`→`accounts.id`. **Валюта НЕ хранится** — берётся со счёта (`accById(p.accId).ccy`)
  на момент рендера (нет рассинхрона при смене валюты счёта). `amt` — в **СЫРЫХ**
  единицах валюты счёта (как `accounts.bal`, НЕ в млн) — чтобы сходиться с
  `calcAccTotals()` (тоже сырые рупии через `toIdr`).
- Backward-compat: `savPots:[]` в `defData` + `if(!Array.isArray(d.savPots))d.savPots=[]`
  в `mergeDefaults`. Новых ключей localStorage НЕ добавлено (ключ прежний `bali_v5`).
- `rPots()`: группирует конверты по цели, считает «Итого отложено» (раскладка по валютам
  → Rp → $), «Свободно» = `calcAccTotals().totIdr − Σ potIdr` (минус → красный
  «Перерасход» + баннер). Полосы: по целям (% от всех денег) и по валютам (% от
  отложенного). Под одну цель можно несколько конвертов с разных счетов.
- Хелперы: `accById/goalById/potIdr` (orphan-счёт→0, не NaN), `potNative`, `ccyAmt`,
  `escapeHtml` (заметки/имена экранируются). Модалка `m-pot` зеркалит `m-acc`
  (`openAddPot/openEditPot/savePot/delPot/fillPotSelects/updatePotCcyHint/updatePotPrev`).
- Удаление счёта/цели НЕ каскадит в конверты (без потери данных): «осиротевший» конверт
  показывается с пометкой «⚠ счёт/цель удалён», `savePot` блокирует сохранение с битой
  ссылкой — нужно перепривязать.
- **`spendGoal(goalId)` — «🎯 Реализовать»** (кнопка в заголовке цели в «Реальном остатке»):
  потратить накопленное — списывает суммы конвертов цели с привязанных счетов
  (`a.bal = max(0, a.bal − amt)`, клампим в 0 при перерасходе счёта), удаляет конверты этой
  цели и ставит `goal.closed=true`. Пример: «Отпуск» — деньги ушли на поездку. Действие
  необратимо автоматически → обязательный `confirm()` с разбивкой по счетам. Зовётся из
  inline `onclick="spendGoal('id')"`, поэтому функция глобальная.
- Цвет цели/категории правится прямо в редакторе (Настройки): `<input type="color" class="ce-color">`
  в `rSavCatEd` и `rCatEd` (onchange → `c.color`, `lsSave`, перерисовка).
- ⚠️ XSS/целостность: пользовательский текст (имена, заметки) вставляется через `escapeHtml`
  (экранирует `& < > "` — кавычка обязательна для `value="..."`). Не вставлять `c.name`/note
  в innerHTML сырыми.
- Кнопки «💾 Сохранить» убраны с разделов только для чтения (Расходы, «План по целям») —
  там нет редактируемых полей, всё сохраняется автоматически при изменении в нужных местах.

## Порядок счетов (Счета)
Порядок карточек = порядок элементов в `D.accounts` (рендерится `rAcc()` в этом порядке).
Перестановка: десктоп — перетаскивание карточек (HTML5 DnD: `accDragStart/Over/Leave/Drop/End`,
карточка `draggable=true`); везде, вкл. телефон — кнопки ◀ ▶ на карточке (`reorderAcc(id,dir)`,
splice в массиве). После перестановки `lsSave()` + `rAcc()`. Обратносовместимо — нового поля нет,
просто порядок массива (сохраняется при синке/перезагрузке). Карточка «Добавить счёт» не draggable.

  (высота из JS) НЕ трогаем.
